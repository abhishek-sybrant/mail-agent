What does the work

Every QuickMail operation in the AI SDR Dashboard takes one of four paths. Which one is never a preference — it is dictated by what QuickMail exposes.

The rule. Use the documented API wherever an operation exists. Drop to QuickMail's internal endpoint only where the API has no equivalent at all. Drive the web UI only where neither API can do the thing. Each step down is more fragile and harder to run unattended, so nothing sits on a lower rung for convenience.

Its limits — which is the whole reason rungs 2 and 3 exist

  • Caps silently. leads(first:) returns 10 however many you ask for. A pass over ~50,000 leads is ~4,800 requests, about 80 minutes at the rate limit — so the lead sync walks a slice per hour and carries a cursor. emailAccounts(first: 100) also returns 10.
  • No company data. The Lead type has no company field and no custom fields. Probed directly: company, companyName, organization, customFields, attributes, website, industry, city, country — all rejected.
  • No campaign pause, no trigger. paused is writable on steps only.
  • Nothing about replies. No message, thread or conversation type exists anywhere in the schema.

2  QuickMail's internal endpoint

The same endpoint QuickMail's own web app uses. Introspection is disabled, so every operation here was recovered by reading their JavaScript bundles — shapes copied from their call sites, never guessed. Their front end defines 326 mutations; we use seven, and five queries.

How the session works. Requests are issued inside the signed-in page via fetch('/graphql'), so the cookie, CSRF token and origin all match. Playwright attaches to an already-running browser over CDP rather than logging in — no QuickMail password is stored anywhere in this app.

Why none of these can use the API

  • Replies. The v2 schema has no reply, message or thread type. v1 REST was probed too — /replies, /inbox, /messages, /threads, /conversations, /emails, /unibox, /activity, /events — every one returns 404.
  • Block lists. No v2 equivalent exists.
  • Deliverability. v2 reports whether a mailbox is connected, never whether its mail lands. The accredited verdict exists only here — and it is what tells us a sender will go to spam.

Quirks that cost real debugging time

  • Two id namespaces. v2 calls a mailbox email_kKXM…; this endpoint calls the same mailbox 198838. Passing the v2 id returns "you don't have the permission to inbox".
  • searchFilter is a JSON string, and required. Omitting it returns a 500 HTML error page, not a GraphQL error.
  • An invented field also returns 500 HTML, naming nothing — which is exactly why shapes are copied from the bundle.
  • first is not obeyed. Asking for 40 returns 30, so paging is explicit. Quiet truncation is how a sync starts looking complete when it isn't.
  • reply_type comes back null on nearly every thread, so reply classification is ours to do.

3  Playwright, clicking the real UI

Used for exactly two things, both confirmed absent from both APIs first: setting the daily trigger (how many new leads start each day) and unpausing the campaign itself, as distinct from its steps.

The most fragile path in the system. It holds a real login rather than an API key, and QuickMail can break it at any time by changing their front end. Three rules follow: it is off unless QUICKMAIL_UI_AUTOMATION=true; it never throws into campaign creation, so a failure degrades to written manual instructions rather than losing a campaign that was created successfully; and every run is verified through the API afterwards.

v1 REST was checked as well before resorting to this: /v1/accounts/{id}/campaigns is a read-only list, and /triggers, /automation, /pause, /resume, /start, plus PUT and PATCH on campaigns, all 404.

The browser, and where it runs

The browser runs on the server, not on your machine. connectOverCDP dials 127.0.0.1, which from the server's point of view is the server. Opening the dashboard from another computer needs no Edge, no Playwright and no QuickMail login — just a browser and an app password.

The server starts that browser itself when it isn't running, using a profile of its own with extensions disabled. One step still needs a person, once: signing in to QuickMail, because no password is stored. The profile keeps the session afterwards.

A consequence worth stating plainly: the automation always acts as whichever QuickMail account that browser is signed in as. It makes no difference who clicks, or from where.

What stops when the browser is unavailable

This is the practical difference between the rungs, and it is visible on the Sync tab every hour. Each part of the hourly pass is recorded independently, so a failed reply pull costs the reply pull and nothing else.
