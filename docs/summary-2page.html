2 The four things QuickMail's API cannot do and how each was solved

Needed Why the API can't Route taken How it works, and what it cost
Read reply content 13 queries, none carry a message body session Their own operation, read out of QuickMail's JavaScript bundle and replayed inside the signed-in page. 374 threads, 1,127 messages.
Send a reply no send mutation exists session replyToEmail — threaded onto the original message, from the mailbox that received it. Verified end to end with a real send.
Set trigger, go live no trigger field; no campaign-level pause UI clicks Playwright fills leads/day, days and time, then flips Paused → Live and handles the warnings dialog. Verified through the API afterwards.
Stop a person's sequence not exposed session setProspectsAsDoNotContact plus cancelProspects — one blocks future enrolment, the other kills what is already queued.
Why not just script the whole UI? Clicking is slow and breaks on every redesign. The browser is used for the session, and real API calls are issued inside it. Clicking is reserved for the two controls that have no operation behind them at all — the trigger and the live toggle.

3 Additions the reason the app exists rather than using QuickMail directly

Addition QuickMail equivalent What it gives us
Human approval gate none — actions are immediate Sending a reply and barring an address each stop at a panel restating exactly what will happen. Both write an audit record of who approved what.
Suppression list per-prospect do-not-contact Keyed on the address, not the prospect row, so re-importing a spreadsheet cannot resurrect someone who asked to stop. Blocks enrolment before it ever reaches QuickMail.
Reply classification returns null on nearly every thread Six-way sentiment on every reply, so 375 threads narrow to the 138 worth a person's time. Accuracy is measured, not asserted — 46 labelled real replies, 65% → 100%.
AI reply drafting none A draft per thread, signed as the mailbox owner, with the quoted history stripped so the model answers the newest message rather than one from three weeks ago.
Campaign agent none Turns a written brief into a full campaign spec — audience, sequence, copy, sending window — then builds it through the API.
Campaign scheduling no start or end date exists A scheduler pauses and unpauses each email variation to enforce a window QuickMail has no field for.
Pre-send guards none Dead-mailbox check, merge-tag validation, suppression gate, and a trailing wait step — each one added after a campaign silently sent nothing.
Full-text reply search subject and sender only Searches the message body too — "the one who asked about pricing" is a likelier search than a name.

6 Needs a decision

38 people asked to stop — 16 explicitly — all awaiting a click
No AI provider funded — quota exhausted, no Claude key
10.5% bounce rate; worst campaign 80.8% against a 5% ceiling
Suppression list holds 9 entries against 42,339 bounces
5 of 17 mailboxes fail sender assignment — support ticket drafted
The standing risk, stated plainly. Reading replies, sending them and stopping a prospect all depend on QuickMail's own internal API, which is undocumented and can change without notice. Campaign creation does not — that uses the published API and is unaffected. Everything built on the internal route fails loudly rather than quietly.
